## Add a title

Illegal-instruction `mtval` uses a younger instruction encoding instead of the faulting instruction

---

## Describe the bug

When XiangShan takes an illegal-instruction exception, `mtval` is written with a nonzero value that is not the faulting instruction encoding.

In the attached reduced repro workload, the failing exception is:

- exception PC / `mepc`: `0x000000008000101c`
- faulting instruction bits: `0x002026f3`
- disassembly: `csrr a3, frm` / `csrrs a3, frm, zero`
- `mcause`: `2` (`Illegal instruction`)

The reference model reports:

```text
mtval = 0x00000000002026f3
```

XiangShan reports:

```text
mtval = 0x00000000c02cf5d3
```

The wrong value `0xc02cf5d3` is not the faulting instruction. It is the encoding of a younger instruction at `PC + 8`:

```text
0x8000101c: 0x002026f3   csrrs a3, frm, zero   <-- faulting instruction
0x80001020: 0x607493bb   rolw  t2, s1, t2
0x80001024: 0xc02cf5d3   fcvt.l.s a1, fs9, dyn <-- value incorrectly written to mtval
```

The attached `xiangshan_difftest_mtval_mismatch.log` was generated by re-running the reduced image. Relevant log excerpt:

```text
[20] exception pc 0000000080001010 inst e20b8953 cause 0000000000000002 fmv.x.d s2, fs7
[25] commit pc 0000000080001014 inst 02696bb3 wen 1 dst 23 data 0000000000000000 idx 018 rem     s7, s2, t1
[26] exception pc 000000008000101c inst 002026f3 cause 0000000000000002 csrr    a3, frm <--
...
mtval: 0x00000000002026f3
...
mtval different at pc = 0x0080001014, right = 0x00000000002026f3, wrong = 0x00000000c02cf5d3
```

Per the RISC-V Privileged Architecture Manual §3.1.16 (Machine Trap Value `mtval` Register): `mtval` may be zero for illegal-instruction exceptions, but if it is written with a nonzero value, it must contain the faulting instruction bits, right-justified with unused upper bits cleared (<https://riscv.github.io/riscv-isa-manual/snapshot/spec/#_machine_trap_value_mtval_register>).

The observed XiangShan value is nonzero but is the encoding of a later instruction, so it violates that requirement.

---

## Expected behavior

For the illegal-instruction exception at `mepc = 0x000000008000101c`, XiangShan should either write zero to `mtval`, or write the faulting instruction encoding:

```text
mtval = 0x00000000002026f3
```

It should not write the encoding of the younger instruction at `PC + 8`.

## Additional context / suspected RTL mechanism

This is not a standalone vector-unit or floating-point execution-result issue. The architectural mismatch is in trap metadata for an illegal-instruction exception.

The reduced repro appears to hit a competition between two sources of illegal-instruction bits:

1. an older CSR instruction, `csrrs a3, frm, zero`, which raises `EX_II` in the CSR permit path because `frm` is an FP CSR while FS is effectively Off;
2. a younger FP instruction, `fcvt.l.s a1, fs9, dyn`, which can be recognized as illegal earlier in decode and stored as pending trap instruction metadata.

The suspected path is:

- `TrapEntryMEvent` fills illegal-instruction `mtval` from `in.trapInst`:
  - `dut/XiangShan/src/main/scala/xiangshan/backend/fu/NewCSR/CSREvents/TrapEntryMEvent.scala:69`
  - `TrapEntryMEvent.scala:85-90`
  - `TrapEntryMEvent.scala:122`
- `NewCSR` passes `io.trapInst` into trap-entry events instead of using the ROB trap instruction directly:
  - `dut/XiangShan/src/main/scala/xiangshan/backend/fu/NewCSR/NewCSR.scala:800-803`
- CSR wrapper drives that value from `TrapInstMod.currentTrapInst`:
  - `dut/XiangShan/src/main/scala/xiangshan/backend/fu/wrapper/CSR.scala:119`
- `TrapInstMod` receives both decode-side illegal instruction metadata and CSR-FU illegal CSR metadata:
  - decode side: `DecodeStage.scala:130-139`, `DecodeStage.scala:301-302`
  - CSR-FU side: `CSR.scala:189-193`, `TrapInstMod.scala:47-59`
- `TrapInstMod.currentTrapInst` is just the currently stored register value:
  - `TrapInstMod.scala:96-97`

In this reproducer, the wrong value exactly equals the younger PC+8 FP instruction. That suggests `mtval` is consuming stale/younger `TrapInstMod` state rather than the instruction associated with the actual ROB trap entry.

A robust fix would bind illegal-instruction `mtval` to the actual trapping ROB entry instruction bits, e.g. use `io.fromRob.trap.bits.instr` for illegal-instruction trap entry, or add a same-cycle CSR-FU illegal-instruction bypass and stricter ROB/FTQ consistency checks to `TrapInstMod`.
